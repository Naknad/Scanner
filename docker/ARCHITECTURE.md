# Архитектура

## Пайплайн end-to-end

```
[Фото этикетки]
      │  (веб-интерфейс: камера/галерея)
      ▼
POST /api/scan  ──────────────────────────────────────────────┐
      │                                                        │
      ▼                                                        │
1. Нормализация фото (app/ocr.py: preprocess)                  │
   grayscale → CLAHE (блики/освещение) → bilateral filter →    │
   deskew (коррекция угла) → adaptive threshold → upscale      │
      │                                                        │
      ▼                                                        │
2. OCR (Tesseract, rus+eng) → сырой текст                      │
      │                                                        │
      ▼                                                        │
3. Нормализация текста (lowercase, снятие диакритики,          │
   чистка пунктуации/пробелов)                                 │
      │                                                        │
      ▼                                                        │
4. Поиск по каталогу (app/matcher.py: CatalogIndex.search)      │
   rapidfuzz.token_sort_ratio по конкатенации                  │
   name+producer+region+grape+category каждой позиции          │
      │                                                        │
      ▼                                                        │
5. Принятие решения (app/main.py: _build_response)              │
   - top1.score < MATCH_MIN_SCORE      → status="not_found"    │
     (+ top5 как "похожие вина")                                │
   - gap(top1, top2) < MATCH_GAP_THRESHOLD → status="ambiguous" │
   - иначе                              → status="found"        │
      │                                                        │
      ▼                                                        │
6. Выдача карточки в JSON  ◄────────────────────────────────────┘
      │
      ▼
[Фронтенд рендерит карточку + виджет «Цифровой сомелье»]
```

Параллельная точка входа `POST /api/predict` использует шаги 1–4 и
возвращает только `{"slug": "..."}` — под формат скрипта оценки
кейсодержателя (шаг принятия решения здесь упрощён до top-1).

## Границы слоёв (модули backend/app)

| Слой                         | Файл           | Ответственность                                             |
|-------------------------------|----------------|---------------------------------------------------------------|
| Нормализация фото             | `ocr.py`       | CV-препроцессинг + вызов Tesseract, нормализация текста        |
| Каталог                       | `catalog.py`   | Загрузка CSV/JSON, построение нормализованного текста позиции  |
| Поиск по каталогу             | `matcher.py`   | Fuzzy-матчинг OCR-текста против индекса каталога               |
| Выдача карточки / API         | `main.py`      | FastAPI-эндпоинты, принятие решения found/ambiguous/not_found  |
| Доп. функционал (удержание)   | `main.py` (`/api/sommelier`) | Правило-ориентированные советы + аналоги по сорту |
| Схемы ответов                 | `schemas.py`   | Pydantic-модели `WineCard`, `ScanResponse`, `FlatPrediction`    |
| Конфигурация                  | `config.py`    | Чтение переменных окружения (пороги, пути, языки OCR)           |

Слои изолированы намеренно: замена OCR на CV-эмбеддинг (следующий этап,
см. ниже) требует правок только в `ocr.py`/`matcher.py`, остальной пайплайн
и API не меняются.

## Почему OCR, а не CV-эмбеддинг, на этом этапе

ТЗ прямо допускает классическое CV/OCR-решение и оставляет применение OCR
на усмотрение команды. Для MVP выбран OCR как более быстрый в реализации и
предсказуемый путь к end-to-end пайплайну в срок, без обучения/дообучения
моделей и без зависимости от GPU. Ограничения такого подхода описаны в
`README.md`.

## Точки расширения (следующие этапы)

1. **CV-компонент по изображению (обязателен по ТЗ для итоговой версии).**
   План: добавить `app/embeddings.py` с SigLIP-подобной моделью,
   считать эмбеддинг фото и сравнивать через pgvector/FAISS с эталонными
   фото каталога; OCR-текст остаётся как усиливающий сигнал (комбинированный
   score = `w1*cv_score + w2*ocr_score`), как рекомендовано кейсодержателем.
2. **Хранилище каталога.** Сейчас каталог грузится в память при старте
   (быстро при 1500–2000 позициях). При переходе на пополняемый каталог
   (~50 позиций/день) — вынести в PostgreSQL + pgvector, как в
   рекомендованном стеке, без изменения интерфейса `CatalogIndex`.
3. **«Цифровой сомелье» на LLM.** `POST /api/sommelier/{slug}` сегодня
   отвечает по правилам; при появлении API-ключа заменить тело функции на
   вызов LLM (OpenAI/YandexGPT/открытая модель) с контекстом карточки вина
   — сигнатура эндпоинта не изменится.
4. **Обработка near-duplicates** (одна этикетка — разные годы/категории в
   серии). План: после OCR-фильтрации по топ-N кандидатам добавить точный
   разбор года/объёма/категории из текста этикетки как второй проход
   ре-ранжирования.

## Соответствие критериям оценки

- **Пайплайн end-to-end** — реализован полностью: фото → OCR → поиск →
  JSON-карточка, отдаётся и в полном (`/api/scan`), и в плоском
  (`/api/predict`) виде для скрипта оценки.
- **Обработка "вина нет в каталоге"** — `status: "not_found"` + список
  похожих вин (`similar`) вместо пустого ответа.
- **Метрика уверенности** — `top1`/`top5` со скорами и `gap` в ответе
  `/api/scan` (в UI не выводится, доступно через API, как и требуется).
- **Дополнительная функция после поиска** — «Цифровой сомелье» (MVP).
- **Docker / воспроизводимость** — единый `docker-compose.yml`, никаких
  внешних сервисов на MVP-этапе.
